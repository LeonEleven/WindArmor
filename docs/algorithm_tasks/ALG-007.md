## 3. Preconditions、inputs / outputs 与软件契约

未来 Candidate 仍须通过现有 factory 创建纯 Python `FlightController`，实现 `reset()` 与
`update(FlightState, positive finite dt)`。Runtime 的 state/command validation 保持前置/后置；
算法不读取 ROS/硬件，也不自行获得 authority。普通 Level B 输出仍是完整当前 motor feedback
position hold、左右 fan `0.0`；非零 absolute rad/fan command projection 是单独评审的前置
契约，当前 `NOT DEFINED / NOT VERIFIED`，不能由 task-local intent 猜测。

Level A/D/E 的 **task-local、software-only** 联合观测至少包含同一帧的
`(pitch_request, roll_request)`、`(pitch_served, roll_served)`、signed residual vector、
`status/disposition` 与继承的 process phase/timeout latch。请求和服务量是无量纲 normalized
软件量，不是 `FlightState`/`FlightCommand` 字段或真实 torque/thrust。合法普通请求各分量位于
`[-1,1]`；pitch 归一化仅沿用 ALG-006 的 `u_pitch/0.10`，roll 的 request 来源、角速度/趋势
语义及与 `0.10` 的关系仍是 Candidate 前置设计项，不得直接套用 pitch gain。每帧同步读取两轴，
不得把同一时刻的组合扰动拆成两个相互独立运行的单轴资格结果。

所有普通输出必须 finite、可重复、有界；每轴服务方向不得与该轴合法非零 request 相反，
零请求不能获得虚构的该轴服务量；`residual_i=request_i-served_i` 保留符号。饱和不能绕过
ALG-004 ordinary pitch envelope/slew 或任何 Level B/底层限制。ALG-005 `TIMED_OUT` 的零是
stop sentinel，优先于普通双轴零；精确 safe-stop 且 latch 只能由显式 reset 解除。

## 5. Multi-axis、耦合、饱和与 arbitration 要求

联合场景须同时改变 pitch/roll，记录逐帧双轴 request、served、residual 与 phase；至少覆盖
同号、反号、大小不等、一个轴先达到限幅及一个轴为零的情况。单轴回归必须保留 ALG-001～006
pitch 语义；roll-only 场景必须有明确 roll 软件方向与中性响应。roll-rate 的未来坐标契约
见 §7；实现及 roll request/control law 仍未完成，不能声称继承了 pitch 的 rate 证据。

资格 fixture 可以定义两个独立轴上限与一个共享的 **synthetic normalized budget**。合法
served vector 必须满足每轴请求/上限及联合预算，residual 显式记录；一轴达到上限但另一轴
仍有软件预算时，不能无理由把另一轴置零。共享预算只是制造竞争的测试约束，不代表电机
或风扇真实 authority。axis caps 与共享预算 `b` **严格只属于 Level A/D/E task-local qualification
fixture 输入**，不是 `FlightState` public fields、runtime hardware authority、measured actuator
capability 或 Candidate configuration。Candidate 不得从 motor/fan health、availability、
`actuation_allowed`、hardware mapping、soft limits、PWM 或 `motor_signs` 推导这些数字。
其具体数值、测试向量与期望关系见 Benchmark §14；任何变化须版本化。当前 Level B 的
nominal axis caps / combined budget 为 **NOT APPLICABLE**；不能由 Level B payload、
`FlightState` 或 runtime 状态推导。未来若有非零 executable projection，须由该独立契约
重新定义软件数值来源和语义，不能表示未经验证的 physical authority。

`b` 与 axis caps 一样必须是非 bool、finite 且位于闭区间 `[0,1]` 的已知软件数字；`None`、
bool、NaN、正负 Inf、负值或大于 `1` 均非法。task-local fixture validation 必须显式拒绝，
或在 task-local seam 进入 `FAIL_CLOSED`；不得 silent clamp、用 tolerance 接受越界，或把未知/
非法 `b` 当作 `0`、`1`。拒绝后不得复用 prior served vector/allocation；若故障到达
controller layer，仍须 exact safe-stop 并清除 ordinary history。

已知合法 zero-capability 与非法输入不同。非零某轴 request 遇到该轴 `cap=0` 时，该轴
`served=0`、signed residual 保留全部该轴 request；另一轴若有合法请求和剩余预算，仍按已
冻结的非竞争关系服务。非零联合 request 遇到合法 `b=0` 时，整个 served vector 为 exact zero，
signed residual 等于 request。两者均不复用旧 allocation，必须可诊断为受影响轴或整个向量的
**INFEASIBLE 语义**；全局 status 及混合场景评分按 Benchmark §14.2 已冻结规则执行。
ordinary zero 才是 `NEUTRAL`；已知正能力不足对应 `SATURATED` 语义；非法输入是
`FAIL_CLOSED`；继承的 `TIMED_OUT` zero 保持独立 stop disposition，五者不得混淆。

已冻结的 arbitration 是先逐轴 cap、再按同一比例缩放以满足 combined L1 budget；
精确公式、零分支、status 优先级和场景期望见 Benchmark §14.2。它是无状态的软件预算规则，
不含 pitch-first、roll-first 或硬件权重。输入校验和 timeout/fault 优先于普通分配；不复用
旧帧。该规则不得绕过继承的 pitch envelope、Level B 或底层限制。

轴耦合只允许 `synthetic / normalized / software stress model`。fixture 应把同一输出向量注入
两个软件状态分量，检验竞争下两个轴不会被彼此遗漏，并记录逐轴状态/趋势和残差；耦合
系数、更新顺序、初态、扰动及 score 见 Benchmark §14.3 的已冻结纯软件 fixture。当前仓库无经过验证的
物理 coupling matrix，故不得把该 fixture 称为 WindArmor 真实动力学。

### 7.1 Current implementation and compatibility audit

当前 `ImuState` 是 `frozen=True` dataclass，字段顺序为 orientation、raw roll/pitch/yaw、relative
roll/pitch、`relative_pitch_rate_rad_s`、angular velocity、linear acceleration、age、
`valid/fresh/connected/zero_generation`；全部字段均无 default，且不存在 roll-rate 字段。仓库内
`ImuState(...)` 直接构造点共 4 个：`ImuAdapter.snapshot()` 的 paired/no-pair 两处 production
构造，以及 `make_fake_flight_state()` / `make_unobserved_flight_state()` 两处 fake helper；均为
keyword construction。仓库测试和文档没有其它直接构造点，但公共模型仍须保护仓库外 positional
caller。

当前 `_validate_imu()` 对所有可选数值先执行 finite 校验；当 `imu.valid=true` 时，orientation、
raw 三轴欧拉角、relative roll/pitch、pitch rate、angular velocity 与 linear acceleration 必须
全部存在，并要求 connected 明确为 true、zero generation 已知、age 已知；`fresh=true` 还要求
`valid=true`。这是当前 base complete measurement set。没有 field-level optional derived
measurement precedent。

`RawImuObservation` 保存规范化 quaternion、由其得到的 raw Euler、同一 raw message 的 body
angular velocity/linear acceleration、派生 pitch rate、source stamp 与接收时刻。`update_raw()`
在写缓存前完成 quaternion、vector、pitch-rate、stamp、重复/乱序校验，任一 source-invalid
条件拒绝整个 update；有效 raw 与 relative attitude 仅按完全相等的正 source stamp 配对。
不匹配的 pending sample 不替换现有 paired snapshot；新完整 pair 才原子替换。freshness 使用
两条消息较早的 monotonic receive time。断线/reconnecting 当前只将 connected 置 false，不清除
pair；zero-generation 改变会清除 pair/pending cache。future roll rate 不得因此复用旧派生值。

ALG-001 只读取 relative pitch；ALG-002～006 读取 relative pitch 与 pitch rate；六个 controller
都依赖 `imu.valid`、`imu.fresh` 和 aggregate freshness，均不读取 roll rate。因此把 roll rate
加入全局 complete measurement set 会让 conditioning-only unavailable frame 收缩全部历史
合格路径的 valid domain，是无必要的 backward-incompatible regression。

### 7.2 Z-Y-X kinematics and conditioning — FORM FROZEN

令同一条 raw IMU sample 的 body angular velocity 为 `(p,q,r)`，规范化 quaternion 按当前
`quaternion_to_euler()` 得到未施加轴向符号的 Z-Y-X `(phi,theta,psi)`：

```text
raw_euler_roll_rate
  = p + sin(phi)*tan(theta)*q + cos(phi)*tan(theta)*r

relative_roll_rate_rad_s
  = roll_axis_sign * raw_euler_roll_rate
```

该公式已用与现有 pitch-rate 测试相同的 quaternion body-rate 微分约定独立作数值导数检查。
把 body rate 到 roll rate 的线性映射写成：

```text
a(phi, theta) = [1, sin(phi)*tan(theta), cos(phi)*tan(theta)]

||a||_2^2
  = 1 + sin(phi)^2*tan(theta)^2 + cos(phi)^2*tan(theta)^2
  = 1 + tan(theta)^2
  = sec(theta)^2

||a(phi, theta)||_2 = 1 / abs(cos(theta))
```

因此 L2 amplification 与 `phi` 无关，并在 `theta -> +/-pi/2` 时无界。这是 Euler coordinate
conditioning，不是 actuator physics、真实恢复能力或硬件安全包络。

现有 `EULER_GIMBAL_LOCK_COS_TOLERANCE=1e-9` 是表示接近数学 gimbal-lock 的 guard，没有证据
证明它限制了可接受 roll-rate amplification。即使 `abs(cos(theta)) > 1e-9`，理论增益仍可任意
接近 `1e9`；所以仅凭现有值宣称 roll rate 数值或语义可接受的答案是 **NO**。

候选无关策略评审：

| 策略 | 020A 结论 |
| --- | --- |
| A. exact-singularity-only | 不控制近奇异点 amplification，不足以冻结 roll-rate availability。 |
| B. `K(theta)<=K_max` | 数学可解释、与硬件 authority 无关，是优先结构；但仓库没有可接受输出误差与 source error bound，无法证明任何具体 `K_max`。 |
| C. `abs(theta)<=theta_max` | 仓库没有 verified mechanical/software attitude envelope；不得发明 `theta_max`。 |
| D. body-frame `p` | 避免 Euler roll-rate 奇异性，但不等同于 `relative_roll_rad` 的时间导数，会改变 v0.5.0-019 coordinate contract；未经 contract revision 不采用。 |

| body/angular-rate magnitude bound | `imu_protocol.py` 的 `GYRO_FULL_SCALE=2000.0` 是 `0x52` wire-decode 的 `deg/s` 满量程实现常量 | implementation constant；不是 reviewed operating bound，未作当前设备/data-path specification verification | 可追踪但不能证明真实 rate envelope、误差或非饱和工作域；不足 |
| body-rate runtime input envelope | `runtime/imu_adapter.py::_finite()` 与 `core/validation.py` 只拒绝非 finite 值，没有 magnitude limit | policy-defined validity domain；已集成 | 适用于当前 path 且 candidate-independent，但没有有限 magnitude bound；不足 |
| controller accepted derived roll-rate error | 未找到 | 无；未冻结、未验证 | 不足 |

| numerical amplification budget | 仅冻结 `K(theta)=1/abs(cos(theta))`；未冻结 `K_max` | mathematical model 已冻结；numerical policy 未冻结 | candidate-independent，但没有 acceptable amplification；不足 |
| verified software operating attitude envelope | `EULER_GIMBAL_LOCK_COS_TOLERANCE=1e-9` 仅是数学/实现 guard；ALG-003 的 `+/-0.004 rad` 等是 synthetic fixture | implementation constant / synthetic；各自在原软件目的下已 review，不是 operating envelope | 不支持 `theta_max` 或 roll-rate guard；不足 |
| verified mechanical/physical attitude envelope | `HARDWARE_REFERENCE.md` 只冻结安装轴向、接线和电机软限位；未给机器人 pitch/roll envelope | hardware mapping / implementation limits；不是 attitude characterization | 与当前硬件相关且 candidate-independent，但不约束机体姿态；不足 |

电机软限位、`motor_signs`、`roll_axis_sign`、fan/motor metadata、ALG-005/007 synthetic 数值及
既有硬件小动作证据都不测量上述 source uncertainty，也不定义 roll-rate output error budget，
故不作为替代证据。审计结果归入 blocker decision tree 的 **Path 3 — Evidence insufficient**。

对冻结映射

```text
f(phi,theta,p,q,r)
  = p + tan(theta)*(sin(phi)*q + cos(phi)*r)
```

其局部灵敏度为：

```text
partial f / partial phi
  = tan(theta)*(cos(phi)*q - sin(phi)*r)

partial f / partial theta
  = sec(theta)^2*(sin(phi)*q + cos(phi)*r)

|| partial f / partial (p,q,r) ||_2
  = 1/abs(cos(theta))
  = K(theta)
```

因此 body-rate vector uncertainty 被 `K(theta)` 放大；roll uncertainty 通过 `tan(theta)` 与
`q/r` 的 magnitude/projection 耦合；pitch uncertainty 通过 `sec(theta)^2` 耦合，且该因子按
`K(theta)^2` 增长，比仅考虑 `K(theta)` 更快。只写
`K(theta)*epsilon_body_rate <= E` 在 orientation uncertainty 非零时遗漏后两项，不能构成完整
derived roll-rate error argument。

工程 guard 必须使用 finite uncertainty，而不只在 nominal point 线性化。若未来存在 reviewed
`epsilon_phi`、`epsilon_theta`，则应在完整区间
`theta in [theta_hat-epsilon_theta, theta_hat+epsilon_theta]` 上分析。该区间若包含任一
`pi/2+k*pi`，就不存在 finite Euler roll-rate bound。否则定义区间 worst cases：

```text
K_I = sup 1/abs(cos(theta))
T_I = sup abs(tan(theta))
S_I = sup sec(theta)^2
```

在另有 `||delta(p,q,r)||_2 <= epsilon_body_rate` 及 relevant transverse body-rate magnitude
`sqrt(q^2+r^2) <= M_qr` 的 reviewed bounds 时，一个保守的 finite-interval Lipschitz 结构才可写为：

```text
abs(delta f)
  <= K_I*epsilon_body_rate
     + M_qr*(T_I*epsilon_phi + S_I*epsilon_theta)
```

其中角度单位为 rad，rate/error 单位为 rad/s；这只是说明所需 evidence 的结构，不是已冻结的
error budget 或 availability rule。当前缺少式中全部 source uncertainty/magnitude bounds，也缺少
可接受输出误差 `E` 或 normative `K_max`，因此不能据此求出常数。

`EULER_GIMBAL_LOCK_COS_TOLERANCE=1e-9` 继续只表示 mathematical / implementation singularity
avoidance。其 accepted side 允许 `abs(cos(theta))` 任意接近 `1e-9`，理论 transformation gain
因而可接近 `1e9`；它不是 sensor uncertainty、conditioning/error budget、software operating
envelope 或 physical/hardware envelope。当前不冻结任何 `theta_max` 或 `K_max`，exact numerical
near-singularity rule 保持 **NOT FROZEN**，020B 保持 **BLOCKED ON NUMERICAL RULE**。

解除 blocker 必须另行 review 以下至少一条路径：完整的 source/body-rate uncertainty、
orientation/pitch uncertainty、relevant rate magnitude 与 accepted derived-output error budget；或
独立 verified 且适用的 operating envelope；或明确的 normative software/API conditioning policy。
最后一条只能标为 software/API policy，不能描述成 sensor capability、hardware envelope、真实
recovery limit 或 physical safety limit。可能需要外部 sensor specification；若它不足，则需要
另行授权的 hardware/sensor characterization。本工作单元两者均未执行。

### 7.3 Public compatibility and fail-close semantics — FROZEN DESIGN

未来字段采用：

```python
relative_roll_rate_rad_s: float | None = None
```

并追加在 `ImuState` 末尾。已有字段全无 default，因此这种 ordering 合法；旧 positional 与
keyword construction 均保持原义，外部 caller 不要求一次性修改。字段是 optional derived
measurement，不加入 legacy/base complete measurement set：

- `imu.valid` 继续表示当前 base IMU pair、连接、zero-generation 和既有完整测量契约有效，
  不代表所有未来 optional derived field 都存在；
- validation 对 roll rate 执行 optional-finite：`None` 合法，finite 合法，NaN/Inf 无论 base
  valid 状态如何均非法；
- source 合法但 conditioning rule 排除时，保留 raw observation/pair，字段为 `None`，不得令
  整体 `imu.valid=false`；
- ALG-007 等需要该字段的 consumer 必须同时要求 `imu.valid`、`imu.fresh`、字段非 `None` 且
  finite，否则 fail-close；ALG-001～006 不因该字段 unavailable 改变行为；
- `None` 精确表示当前 snapshot 没有可用的 roll-rate 派生测量，包括 no pair、conditioning
  exclusion 或 lifecycle invalidation；它不表示零，也不允许补入 prior value；
- stale pair 可以保留属于旧 snapshot 的 finite 值，但 `fresh=false`，consumer 不得把它作为
  fresh trend；disconnect/reconnect 或 zero-generation transition 后，在新的完整 pair 到达前
  roll rate 必须为 `None`，即使为兼容 base pair 的其它字段仍被保留。

不新增 `relative_roll_rate_valid`、`roll_rate_available` 或 reason enum。`None` 加现有
`valid/fresh` 已能无歧义表达 consumer prerequisite；诊断原因可以保留在 Runtime 内部日志/状态，
目前没有无法由该组合表达的公共安全需求。

必须区分：SOURCE INVALID（非法 quaternion、非有限 body rate、非法 stamp、重复/乱序等）继续
拒绝 raw update；DERIVATION UNAVAILABLE 是 source 本身合法但不满足未来 conditioning rule，
必须保存 raw observation，并将 roll rate 置 `None`。后者不能污染或丢弃 base sample。

### 7.4 roll-axis sign, same-sample and lifecycle contract — FROZEN DESIGN

relative attitude producer 已使用 `imu_cybergear_params.yaml` 的 `roll_axis_sign` / `pitch_axis_sign`
（默认均 `1.0`），先对 raw Euler 乘 axis sign，再 normalize，最后减 zero offset 并再次
normalize。共享 motor config parser 先拒绝 bool/非有限值再严格要求 `+1/-1`；实际 relative
observer callback 依赖已声明的 ROS double parameter type，并用 membership 检查 `+1/-1`，其
Python 条件本身没有显式排除 bool。020B 必须使 producer/consumer 的显式校验都拒绝 bool、0、
其它数值及非有限值，并增加对应测试。

Flight Runtime 当前只从 `flight_control.yaml` 读取 `pitch_axis_sign` 并传给 `ImuAdapter`；没有
roll sign。020B 的最小兼容 migration 是在 RuntimeConfig、Flight YAML 与 `ImuAdapter.__init__`
增加同名 `roll_axis_sign`，默认 `1.0`，沿用 producer 已有 key 和严格 `+1.0/-1.0` 校验。Flight
与 producer 仍是两个 node-scoped parameter source，因此必须用 repository configuration test
比较两边明确值，并分别用非对称 signs 验证 roll/pitch 没有 wiring 互换；不能依赖相同 implicit
default。不得从 `motor_signs`、actuator mapping、CAN ID 或 fan mapping 推断。

roll rate 必须由同一 composite ROS `Imu` message 的规范化 orientation 与 body angular velocity
计算；使用 raw
`phi/theta`，最后才施加 `roll_axis_sign`。不得有限差分 relative angle、不得使用 zero offset、
不得跨 composite ROS message 混合、不得复用上一帧。raw observation 只有与相同 source stamp 的 relative attitude
配对后才进入 snapshot。conditioning-unavailable 的新完整 pair 必须原子替换旧 pair 的 roll-rate
availability；disconnect/reconnecting transition 使旧 roll rate 失效，reconnect 后需新完整 pair；
zero-generation 改变继续清除 pair/pending state。这里的 ROS message 同一性不证明底层厂家
`0x52` 与 `0x53` 属于同一 module update/cycle；该更底层前置条件见 §7.8。

### 7.8 IMU data-path provenance and sample-coherence prerequisite — v0.5.0-020A.2 FROZEN

本节是 docs-only / evidence-only prerequisite freeze，不修改 parser、driver、Runtime、配置或测试，
也不选择未来 coherence mechanism。厂家事实来自人工已审查的《用户手册》、
《10轴IMU模块通讯协议》、两份 IMU 应用教程、原理图、模型图纸与 `IMU.stp` 的 external evidence
handoff；这些资料不是 repository-tracked normative specification，本工作单元也不声称独立读取或
验证了原始 PDF/模型。必须区分三层 provenance：

1. **Vendor documented default**：厂家资料记录的默认行为或参数；
2. **Owner operational history**：owner 确认该实际 IMU 只使用厂家上位机做过功能测试、未主动
   修改配置，因此该物理设备合理预期仍为厂家默认；
3. **Runtime/source-controlled verification**：WindArmor 当前没有在启动或重连时 write 或 readback
   verification 这些关键模块配置，故不能称为 `VERIFIED DEFAULT`。

#### 7.8.1 Current active data path

当前 `develop` 的 production path 已从下列实现重新核对：

| Vendor frame | Vendor meaning | Current WindArmor handling |
| --- | --- | --- |
| `0x50` | TIME | **NOT PARSED / NOT USED** |
| `0x51` | ACC | parsed to acceleration cache |
| `0x52` | GYRO | parsed to module-reported angular velocity；deg/s → rad/s |
| `0x53` | ANGLE | parsed to Euler roll/pitch/yaw；triggers composite ROS `Imu` publish |
| `0x54` | MAG | recognized but ignored |
| `0x59` | QUATERNION | **NOT PARSED / NOT USED** |

- `imu_cybergear_ros2/imu_protocol.py` 的 `WitImuFrameParser.parse_byte()` 解析 `0x51 ACC`、
  `0x52 GYRO` 和 `0x53 ANGLE`；`0x54 MAG` 被忽略，未实现 `0x50 TIME` 或 `0x59 QUATERNION`；
- `0x52` 使用 `signed_int16 / 32768 * 2000 deg/s` 后转换为 `rad/s`，形成 WindArmor parsed
  angular velocity；
- `0x53` 使用 `signed_int16 / 32768 * 180 deg` 得到厂家 Euler roll/pitch/yaw；
- `imu_cybergear_ros2/imu_driver_node.py` 的 `_publish_imu()` 将该 Euler 转为 rad，再经
  `quaternion_from_euler()` 生成 ROS `(x,y,z,w)` orientation；
- `imu_relative_observer_node.py` 或 `imu_motor_controller_node.py` 从该 ROS orientation 重建
  relative roll/pitch；Flight `runtime/imu_adapter.py` 规范化同一软件生成的 quaternion，再按
  Z-Y-X 重建 Euler、派生 pitch rate，并把 raw/relative ROS 观测按完全相等的 header stamp 配对；
- `observations.py`、`state_aggregator.py`、`core/models.py` 与 `flight_control.yaml` 承接观测、
  `0.2 s` freshness 和公开 `ImuState`，不增加厂家 cycle identity。

因此 authoritative vendor orientation source 是 **`0x53 ANGLE` Euler**，不是 `0x59`；ROS
quaternion 是 **SOFTWARE-DERIVED FROM VENDOR EULER**，下游又从该表示重建 Z-Y-X Euler。
厂家 quaternion quantization 当前不适用。厂家 `0x52` 应称为 **module-reported angular
velocity**：模块存在 offset、auto-calibration、filtering、static detection 与 low-rate
zeroing/threshold 行为，现有证据不能把它等同于 physical raw MEMS rate。

#### 7.8.2 Composite ROS message versus vendor update/cycle

`WitImuFrameParser` 为 ACC、GYRO、ANGLE 分别保存 latest cache；只有合法 `0x53` 使
`parse_byte()` 返回 true。driver 随后读取 latest ACC + latest GYRO + current ANGLE，写入一条
`sensor_msgs/Imu`，并在此时生成新的 ROS timestamp。parser 没有 vendor sample/cycle ID、
per-frame source timestamp、完整 module-update generation，也不使用 `0x50 TIME`。

所以当前证据只支持：

- **same composite ROS `Imu`：CURRENTLY AVAILABLE**；gyro/orientation 被包装在同一 ROS
  message，raw/relative downstream messages 可按该 ROS stamp 配对；
- **same vendor module update/cycle：NOT PROVEN**；ROS stamp 是 composite publish time，不能
  反证独立 serial frames 属于同一次厂家更新。

当前实现允许、至少不能排除以下 software-visible sequence：`GYRO_N` 后 `ANGLE_N` 形成正常
composite；若 `GYRO_N+1` 丢失或校验失败而 `ANGLE_N+1` 到达，latest cache 可形成
`GYRO_N + ANGLE_N+1`，并赋予新 ROS timestamp。serial reconnect 只重开 transport，当前没有
证明 parser partial-frame state 和 ACC/GYRO/ANGLE component cache 被清空；因此 reconnect 后若
先到 `ANGLE_new`，也不能排除 `GYRO_old + ANGLE_new`。这些是静态实现允许的 failure mode，
**不是已在硬件上观察到的故障**。fresh ROS timestamp 可能令 downstream 无法识别内部 component
已经陈旧。

020A 的 logical same-sample contract 保持不变；020A.2 冻结其底层 prerequisite：未来
implementation 必须建立可审查的 **coherent composite-sample rule**，其 observable semantics
至少满足：

1. previous gyro 不得与 new angle 形成可用新 sample；
2. reconnect 前 component 不得与 reconnect 后 component 组合；
3. fresh composite timestamp 不得掩盖 stale internal component；
4. disconnect/reconnect/reset 必须清除或代次隔离 parser partial state、ACC/GYRO/ANGLE cache、
   pending composite state 及其它 prior-reuse source；
5. downstream freshness 只能由 reconnect/reset 后新完成的 coherent composite sample 建立。

允许未来评审 expected-frame-cycle state machine、`0x50` source time、monotonic module cycle、
complete ACC/GYRO/ANGLE set、reconnect generation 或其它 bookkeeping；本 freeze 不预选实现结构。

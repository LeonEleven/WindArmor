## Executive summary

The repository has strong safety contracts and unusually complete v0.4.0 hardware evidence,
but the documentation hierarchy still reflects the order in which Flight integration was built.
It does not yet provide a safe, continuous newcomer path from a first controller through unit
testing, meaningful DRY_RUN observation, review, and bounded hardware smoke testing.

Five P0 release blockers were found:

1. `FLIGHT_CONTROL_API.md` still says Flight takeover has no real-hardware verification.
2. `FLIGHT_CONTROL_ARCHITECTURE.md` repeats the same obsolete blanket claim.
3. `FLIGHT_CONTROL_API.md` describes `required_inputs_fresh` too broadly; source currently
   computes it from paired IMU plus all configured motor feedback, not every safety/fan input.
4. `src/imu_cybergear_ros2/README.md` still documents the removed cold-start `0.0 rad` target
   behavior, which conflicts with the measured-position hold implementation and safety record.
5. The historical v0.3.2 RC checklist still tells an operator to confirm GPIO12/13 without a
   prominent historical-only warning; current hardware uses GPIO12/26 and reserves GPIO13 for
   CAN HAT INT_1.

The repository does already contain and has physically exercised a controller-to-real-motor-and-
fan path. `BoundedVerificationController` is loaded by the normal factory contract, captures a
fresh per-authority motor baseline, applies one bounded offset while holding the other motors,
emits both fan commands, passes through Runtime `/flight_control/command`, and is consumed by the
existing motor and fan managers. Gate B and Gate C provide real-hardware evidence for this path.
It is deliberately a verification controller and is not suitable as a newcomer template.

Recommendation: retain `FLIGHT_CONTROL_API.md` as a compact field/interface reference, move
Runtime/authority internals to `FLIGHT_CONTROL_ARCHITECTURE.md`, add a step-by-step
`ALGORITHM_DEVELOPER_GUIDE.md`, add a dedicated non-default educational controller, and move the
release-specific Gate narrative into one versioned verification record. Do not delete hardware
evidence or invalidated-attempt history.

## Newcomer algorithm developer findings

### Current actual path

A newcomer currently has to infer this sequence:

1. Find the short algorithm entry at `README.md:102` after a long release-status preamble.
2. Read the mixed tutorial/reference/Runtime narrative in `FLIGHT_CONTROL_API.md`.
3. Inspect `algorithms/example_controller.py`, `core/models.py`, and
   `test/test_example_controller.py` to learn the real construction pattern.
4. Implement `reset()` and `update()` and return a complete four-motor/two-fan frame or
   `FlightCommand.safe_stop()`.
5. Add a module-level factory and set `controller_factory` to `module.path:function`.
6. Build fake states and run a selected pytest file.
7. Launch `flight_control_dry_run.launch.py` and discover that it starts only Runtime. Without
   external state publishers it can show safe startup behavior but not a meaningful sensor-driven
   algorithm demonstration.
8. If live WindArmor state is desired, separately arrange the real state-producing system; that
   crosses hardware authorization boundaries even though Runtime itself remains non-actuating.
9. For hardware, stop being the sole actor: a maintainer/operator must review the controller,
   define bounded values, prepare evidence/watchdogs, authorize the exact scenario, and execute it.

### Main gaps

- There is no first-day tutorial or end-to-end review checklist.
- The API reference introduces authority, epoch, generation, ownership, cutoff, commit, lease,
  rollback, and transport envelope before a newcomer needs those internals.
- The default `NeutralExampleController` is useful as a fail-closed API fixture, but in DRY_RUN it
  sees `actuation_allowed=false` and returns only safe-stop. It does not demonstrate
  attitude-input-to-command-output behavior.
- There is no bundled simulated-state provider or software-only ROS demo launch. Current DRY_RUN
  alone is safe but not a complete sensor-driven demonstration.
- No tutorial explains how to edit a fake state with `dataclasses.replace`, assert a specific
  attitude-to-output relationship, or test reset/stateful behavior.
- Motor logical names, their physical meaning, coordinate reference, and command sign are split
  between config, hardware reference, package source, and verification history.
- `dt`, `None`, `valid`, `fresh`, `healthy`, safe-stop, and full-frame semantics are documented,
  but not in a progressive order or with common failure examples.
- No clear boundary says: Level 1 is developer-owned; meaningful live-state DRY_RUN may require an
  operator; Level 3 is maintainer/operator-owned and is never a self-service hardware command.

### Dedicated example recommendation

Add a non-default `example_algorithm_controller.py` (or equivalently named attitude example)
rather than turning `BoundedVerificationController` into teaching material. It should:

- remain pure Python and have no hardware/ROS imports;
- transform a small, explicit fake relative-roll/pitch input into an easily asserted complete
  `FlightCommand`;
- demonstrate unknown/stale input and `reset()` behavior;
- be selectable for DRY_RUN without changing the default takeover-disabled safety posture;
- carry no claim that zero targets, gains, offsets, fan commands, or directions are real-hardware
  tuning;
- have a companion unit test and a software-only demonstration path.

Keep `NeutralExampleController` if it remains useful as the minimal fail-closed contract fixture.
Do not present `BoundedVerificationController` as the first algorithm: its authority-session
baseline and verification guards are deliberate release-verification behavior.

A separate `docs/ALGORITHM_HARDWARE_SMOKE_TEST.md` is recommended because operator commands and
ten-item authorization data should not dominate the newcomer tutorial. It should be a reusable,
maintainer/operator-owned process linked to `AGENTS.md` and the release verification record, not a
copy of all v0.4.0 Gate attempts.

## Algorithm test path: Unit → DRY_RUN → Bounded Hardware

| Level | Current/recommended path | Algorithm developer owns | Maintainer/operator owns | Promotion gate |
|---|---|---|---|---|
| 1 — Unit Test | fake `FlightState` → `update()` → validate/assert `FlightCommand`; no ROS/hardware | controller, fake cases, unit semantics, safe-stop/reset tests | API review if semantics change | Tests green; complete frame; units/signs/None behavior reviewed |
| 2 — DRY_RUN | Runtime → state adapter → controller → status/preview; no actuator authority | run software-only demo, inspect preview/status, debug loader/logic | provide/approve live state source if it touches real IMU/CAN; add synthetic provider | Meaningful preview over normal/stale/unknown cases; takeover remains false |
| 3 — Bounded Hardware Smoke | reviewed controller → explicit authorization → bounded values → Runtime/authority/managers → real actuator + continuous evidence | submit algorithm, tests, intended bounded behavior and stop conditions; observe results | define exact scenario, verify config, prepare recorder/watchdog, obtain ten-item authorization, operate power/hardware, classify evidence | P0/P1 docs/tests resolved; reviewed limits; operator authorization; safe shutdown/evidence plan |

Current limitation: Level 2 has no bundled simulated state publisher. Starting
`flight_control_dry_run.launch.py` alone is safe and non-actuating, but normally yields unknown
state/default safe-stop until other publishers exist. Connecting it to live state is not a blanket
software-only action; the source nodes may access serial/CAN/GPIO and require authorization.

An algorithm developer must not independently enable `flight_takeover_enabled`, select the bounded
verification factory with real values, call authority prepare, start hardware launch, publish
actuator envelopes, reset E-STOP/ERROR, set zero, or energize actuators.

## Simple algorithm to real motor/fan evidence

Fact classification:

- **A — pure unit evidence:** `test_bounded_verification_controller.py` covers configuration
  fail-close, complete baseline frame, one fixed offset, non-accumulation, fan values, reset,
  session changes, and stale/invalid inputs. Loader/model/envelope tests cover the surrounding
  pure contract.
- **B — Runtime integration evidence:** Runtime handoff tests cover factory-loaded controllers,
  state validation, reserve/commit, atomic cutoff, post-cutoff commands, `/flight_control/command`,
  safe-stop, rollback, and owner loss; motor/fan integration tests cover each consumer.
- **C — real hardware evidence:** the v0.4.0 verification record documents Gate B1 motor bounded
  takeover, B2 LEFT fan bounded takeover, and Gate C C1/C2/C3/C4a/C4b fail-closed scenarios using
  the bounded controller through the real Runtime/authority/manager path.

`BoundedVerificationController` facts confirmed from source:

- it structurally satisfies `FlightController` (`reset` + `update`);
- it captures all configured motor positions only from valid/fresh/healthy feedback in the current
  positive authority epoch/generation;
- it adds one configured offset to one selected logical motor and holds every other baseline;
- it does not accumulate the offset and discards/re-captures baseline on invalid/session changes;
- it returns configured left/right `FanCommand` values;
- its factory is guarded by Runtime-validated verification configuration;
- Runtime sends its valid ACTIVE result as the only `/flight_control/command` envelope stream;
- motor and fan consumers independently validate and route it through existing managers/safety.

Why it is not a newcomer template: its name and module are verification-specific, it requires
authority/session and explicit verification guards, it is unusable by default, and its baseline
logic is designed for bounded hardware evidence rather than explaining basic algorithm design.

# WindArmor v0.4.0 Hardware Verification Plan

> Status: PLANNED / NOT YET EXECUTED
>
> 当前正式 stable release 仍为 `v0.3.2`。v0.4.0 Flight takeover 尚未经过
> 真实硬件验证。本文档是未来执行协议，不构成任何硬件操作授权。

每个 Stage 都必须由用户单独、明确授权；某 Stage 通过不自动授权下一 Stage。
任一 Stage 失败后默认停止、记录证据并回到安全状态，不自动继续。所有带电 Stage
在执行前还必须逐项满足根目录 `AGENTS.md` 的十项带电测试授权门槛。

## 1. Scope and execution status

本文档规划 Stage 0–9 的真实硬件验证顺序、授权边界和证据要求。本计划不执行
Stage 0–9，不修改控制逻辑、launch 默认值或 config，不进入 v0.4.0 RC/release。

截至本计划编制基线 `413dbc1`，只允许把 Stage 0 提交给用户选择是否执行。
Stage 1–9 受第 4 节列出的执行 blocker 限制；在对应 Task 6.x 完成、纯软件 CI
通过并重新审查本计划前，状态均为 `BLOCKED / NOT AUTHORIZED`。

验证哲学与固定顺序为：

```text
physical confirmation
-> read-only observation
-> ownership reservation without motion
-> single-subsystem takeover
-> bounded actuator command
-> combined takeover
-> timeout/fault injection
-> legacy regression
```

这里的顺序是安全 gate，不是自动流水线：

- Stage N 的 PASS 只提供 Stage N+1 的一项 prerequisite；
- Stage N 的授权不延续到 Stage N+1，也不延续到同一 Stage 的另一种带电场景；
- motion、owner takeover、process crash、E-STOP/fault injection 分别重新授权；
- 任何 `FAIL` 或 `NOT VERIFIED` 都阻止依赖该项的后续 Stage；
- software-only/fake/mock 证据只能作为硬件前置 gate，不能记为实机 PASS。

## 2. Common execution contract

### 2.1 Result vocabulary

每项记录只能使用：

```text
PASS / FAIL / NOT VERIFIED
```

`PASS` 必须有正式 evidence record；未执行、没有观测来源或无法确认的项目写
`NOT VERIFIED`，不能凭默认配置或历史经验补写 PASS。

### 2.2 Pre-execution safety checklist

任何带电 Stage 前逐项确认并记录：

- [ ] Git HEAD 正确，且记录 `git status --short --branch`；
- [ ] 当前 working tree 与批准的执行基线一致；
- [ ] motor、fan、Flight config snapshot 已保存；
- [ ] exact launch、ROS 命令、参数文件和 controller factory 已逐条复核；
- [ ] 机器人固定可靠，机械活动范围内无人；
- [ ] 机械活动空间、负载和支撑适合本 Stage；
- [ ] 电机动力、风扇动力和逻辑电源的物理断开方式可立即操作；
- [ ] `/e_stop` 操作方式可用且操作人可触及；
- [ ] 风扇有防护，进出风区域无人、无线缆或松散物；
- [ ] motor load mechanically safe；
- [ ] terminal/log capture 已开启且时间同步可用；
- [ ] ROS graph 中没有 stale node、publisher、service 或重复控制进程；
- [ ] previous Flight authority 已清除，两路 owner 均不是旧 Flight token；
- [ ] 没有 old Runtime process；
- [ ] 用户已明确授权当前 Stage 及当前子场景；
- [ ] `AGENTS.md` 十项授权内容已逐项记录。

### 2.6 Global stop conditions

以下任一条件立即触发统一停止规则：

- motor 实际方向与批准预期不一致；
- fan 左右通道或旋转方向不一致；
- command target、logical name、CAN ID 或实际响应不匹配；
- motor fault bit、温度 warning 持续恶化或达到 critical temperature；
- CAN/serial/transport 不稳定；
- IMU axis/sign 与物理姿态不一致；
- owner state unknown、错误、过期或 token 不符合当前 attempt；
- 需要 clear 时 global E-STOP 不是明确 `false`；
- unexpected authority epoch/generation；
- command sequence 重复、乱序、跳变或 first accepted sequence 异常；
- unexpected `ACTIVE`、unexpected actuator path 或 stale readback；
- handoff/command/owner-readback lease timeout；
- 未批准的 actuator movement；
- 机械干涉、支撑松动或活动范围不足；
- 异常声音、振动、气味、温升或热量；
- 日志/观测丢失，无法证明当前状态；
- 用户或现场安全观察员要求停止。

发生任一条件：

```text
STOP current stage
do not auto-continue
record evidence
return to safe state
```

### 2.7 Recovery rules

- ERROR 不自动恢复；排除原因后走现有 lifecycle 重新配置或重启流程；
- E-STOP clear 不恢复 Flight；
- transport reconnect 只恢复通信，不恢复 Flight 或 legacy command；
- Runtime restart 不恢复 authority；
- old epoch/generation command 永久无效；
- owner timeout 后不自动 legacy；
- Flight safe-stop 后不自动 legacy；
- next attempt 必须 explicit reset-inhibit（如适用）及新的 prepare/handoff；
- legacy reclaim 必须由 operator 显式操作；
- 不为方便测试设计自动恢复、旧目标重放或 authority 复用。

### 2.8 Prohibited destructive testing

常规 v0.4.0 验证不得：故意堵转、超过 soft limit、升温到 critical、制造过流、
破坏 CAN bus、带电拔插高功率线、触碰旋转风扇、超过当前 Flight fan max、修改
safety threshold 制造故障、绕过 E-STOP/watchdog，或直接写 CyberGear SDO
代替正式路径。

## 4. Current software blockers and Task 6.x gate

只读接口审计发现以下 blocker。它们不在 Task 6 修改，但必须在进入对应硬件
Stage 前由独立 Task 6.x 解决，并同步本计划的 exact commands。

### B1 — Stage 1 没有完整的 powered read-only state path

- `imu_cybergear_system.launch.py start_controller:=false` 只允许读取真实 IMU raw/status；
- `/imu/relative_roll_pitch` 和 `/imu/zero_generation` 由 motor controller 发布；
- motor controller configure 会连接 CAN、写 run mode/速度/目标位置 `0.0` 并进入
  控制模式，启动本身可能造成运动；
- `/motors/feedback` 与 `/motors/safety_state` 也由该 controller 发布；
- `fan_controller` 构造时占用 GPIO12/13、输出 stop PWM 并执行 ESC arm delay；
- `/fans/status_pwm` 与 `/fans/enabled` 依赖该硬件节点。

因此当前仓库不能在“不发送任何 actuator command”的 Stage 1 中完成完整
`hardware -> structured ROS state -> FlightState` 链路。需要 Task 6.x 提供并验证
真正只读的观测路径，或由用户明确批准重新定义 Stage 1 的初始化风险；后者不得
继续称为 read-only。

### B2 — Production Runtime 不能停在 reserve 后等待人工 revoke

`flight_takeover_enabled=true` 时，Runtime 在 READY 后自动开始 motor/fan reserve，
两路成功后自动 commit，再在 readback 齐全时 atomic commit。当前没有生产接口在
reserve 与 commit 之间暂停。直接手工调用 owner service 可以验证 owner endpoint，
但不能证明 Runtime 的正式 handoff 顺序，且不得伪装成 production Runtime 验证。

Task 6.x 需提供受测试的 staged verification mode/工具，或批准一个不改变安全语义
的正式验证入口；在此之前 Stage 2 只保留接口模板，不执行。

### B3 — 没有可安全执行的 bounded hardware test controller

当前 factory 创建 `NeutralExampleController`。其全零 motor frame 在源码中明确不是
机械中位，ACTIVE 后可能把一个或多个电机从当前位置推向 `0.0`。仓库也没有可在
实机前设置单轴小幅 offset、保持其他电机当前位置并保持 fan stop 的正式 controller。

Task 6.x 必须提供 pure-tested、配置显式、首次命令以 fresh feedback 为基准、幅度
在执行前填写且可 safe-stop 的 test controller。最大偏移现在记为：

```text
TO BE SET BEFORE EXECUTION
```

不得使用默认示例 controller 代替，不得为此修改 soft limit、speed limit 或
`motor_feedback_timeout_sec`。

### B4 — 正式 envelope/Runtime 是 combined ownership contract

normal `FlightCommandEnvelope` 必须同时包含完整 motor frame 与 fan payload；Runtime
必须获得 motor/fan 两路 ownership 后才能 ACTIVE。因此 Stage 3/4 当前只能设计为
“单 subsystem 产生非停止动作、另一 subsystem 接收 hold/stop payload”，不能声称
获得单一 owner takeover。若验收要求真正 motor-only 或 fan-only ownership，需先由
Task 6.x 明确架构和兼容迁移；Task 6 不做该控制逻辑变更。

## 6. Stage 1 — Powered read-only state verification

**Risk level:** MEDIUM

**Hardware scope:** IMU、Motor/CAN、Fan/GPIO/PWM、Flight Runtime

**Prerequisites:** Stage 0 PASS；software gate green；B1 已解决并有新 review；actuator
动力默认断开；所有 state source 的启动副作用已逐项确认。

**Required explicit user authorization:** 是。IMU 串口访问、motor/CAN 观测和
fan/GPIO 观测分别列出并授权；一个授权不涵盖另一个域。

**Allowed operations:** 只读 echo/记录；默认 takeover=false 的 DRY_RUN preview；
不调用 owner/actuator/recovery service。

**Forbidden operations:** actuator command、owner reserve/commit、Flight takeover、
motor enable/set-zero、fan enable/manual/auto、E-STOP/fault injection。

**Exact launch / ROS commands:** 当前完整 Stage 被 B1 阻止，不得执行。现有唯一
可独立授权的 IMU raw 子集命令是：

```bash
ros2 launch imu_cybergear_ros2 \
  imu_cybergear_system.launch.py start_controller:=false
ros2 topic echo /imu/data_raw sensor_msgs/msg/Imu
ros2 topic echo /imu/status std_msgs/msg/String
```

该命令访问 `/dev/imu_usb`，必须先取得 IMU 访问授权；它不能产生
`/imu/relative_roll_pitch`、`/imu/zero_generation`、motor state 或 fan state，不能
记作 Stage 1 PASS。默认纯 observer Runtime 命令为：

```bash
ros2 launch windarmor_flight_control flight_control_dry_run.launch.py
ros2 topic echo /flight_control/dry_run/status \
  windarmor_interfaces/msg/FlightRuntimeStatus
ros2 topic echo /flight_control/dry_run/command_preview \
  windarmor_interfaces/msg/FlightCommandPreview
ros2 topic echo /flight_control/authority/status \
  windarmor_interfaces/msg/FlightAuthorityStatus
```

在 B1 解决前，以下仅是已核对的只读观测接口清单，不是启动 lower-level nodes 的
授权：

```bash
ros2 topic echo /imu/relative_roll_pitch geometry_msgs/msg/Vector3Stamped
ros2 topic echo /imu/zero_generation std_msgs/msg/UInt64
ros2 topic echo /motors/feedback windarmor_interfaces/msg/MotorFeedbackArray
ros2 topic echo /motors/control_mode std_msgs/msg/String
ros2 topic echo /motors/safety_state windarmor_interfaces/msg/MotorSafetyState
ros2 topic echo /fans/status_pwm std_msgs/msg/Int32MultiArray
ros2 topic echo /fans/enabled std_msgs/msg/Bool
ros2 topic echo /fans/control_state std_msgs/msg/String
ros2 topic echo /fans/safety_state windarmor_interfaces/msg/FanSafetyState
```

**Expected ROS state:** Runtime `DRY_RUN`；authority `NONE`；authority generation `0`；
`flight_control_active=false`；`actuation_allowed=false`；只有 preview，无
`/flight_control/command` publisher。IMU connected/zero_generation、四逻辑电机和
fan state 都必须来源明确、valid/fresh 语义正确。

## 12. Stage 7 — E-STOP / ERROR interaction

**Exact launch / ROS commands:** E-STOP 正式接口为：

```bash

```

未来 clear/recovery 只有在停止证据确认、原因排除和独立授权后才可执行：


```text

```

**Expected ROS state:** lower-level E-STOP 优先；Flight authority 失效；motor/fan safe；
Runtime INHIBITED；clear 后仍不恢复 Flight；需要既有 explicit recovery 加新的 prepare。

**Expected physical behavior:** E-STOP 后 motor/fan 立即进入既有安全状态；clear 不产生

E-STOP 聚合、owner/Runtime 变化、stop evidence、clear 后保持状态、ERROR reason/latch。

**Abort / stop conditions:** 任一 actuator 未停、E-STOP clear 自动 ACTIVE、Flight 能
clear ERROR、reconnect/restart 重放旧 target。

**Rollback / safe-state procedure:** physical power cut；保持 E-STOP/ERROR latch；不
继续恢复；保存 evidence 并单独诊断。

**Pass criteria:** E-STOP 优先级、latch、无自动恢复和新 prepare 要求均符合契约；

**Fail criteria:** lower-level override、latch 或 stale authority isolation 任一失效。

**Next-stage gate:** 完全恢复到已确认 safe startup 后，单独授权 Stage 8。

## 17. Plan maintenance rule

任何 Task 6.x、config、launch、topic/service、message、owner phase、timeout、recovery
或 controller factory 变化后，必须先更新第 4、5–16 节并重跑 software gate。
实际 Stage 记录只引用本计划版本和证据文件，不把一次性聊天内容当作 protocol。

本计划完成不等于 Stage 0 已执行，也不等于任何设备已获准上电。下一步只能由用户
单独选择并授权 Stage 0；Stage 1–9 在 blocker 关闭前保持禁止。

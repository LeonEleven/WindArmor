## 2. Common contract

### 2.1 Evidence and software gate

结果只允许 `PASS / FAIL / NOT VERIFIED`。每个子场景记录：日期、操作人和安全
观察员、Git HEAD/status、配置文件 hash、授权记录、各电源状态、authority epoch、
generation、两路 owner token/source sequence、state/command sequence、预期、实测、
停止原因、退出后安全状态及日志位置。

每次硬件 session 前先在 actuator 动力断开、且不启动任何硬件 node/launch 时执行：

```bash
cd ~/workspace/WindArmor
git rev-parse HEAD
git status --short --branch
source /opt/ros/jazzy/setup.bash

```

CI 必须 green，且执行基线必须与记录一致。CI 是纯软件证据，不是实机 PASS。

### 2.2 Fixed configuration facts

- motor logical names：`left_lift, left_pitch, right_pitch, right_lift`；
- CAN ID 映射：`4, 3, 2, 1`；算法和人工命令只使用 logical name；
- `motor_signs`：`[-1.0, 1.0, -1.0, 1.0]`；
- motor limits：`[-1.57,-1.57,-1.57,0.0]` 到 `[0.0,1.57,1.57,1.57]`；
- `motor_feedback_timeout_sec=0.0`，不得为验证而改变；
- fan GPIO：left GPIO12、right GPIO26；首次带电前必须物理确认 GPIO26；GPIO13
  保留给 Waveshare 2-CH CAN HAT+ 的 CAN_1 INT_1，不再用于右 fan；
- `flight_fan_max_pwm_us=1400`，normalized command 不是 thrust fraction；
- `flight_takeover_enabled=false`、`verification_controller_enabled=false`；
- `motor_test_offset_configured=false`，仓库没有获准的真实 offset；
- fan test command 默认 `0.0 / 0.0`。

Gate B/C 使用 controller factory：

### 2.3 Continuous evidence workflow

后续瞬态硬件验证统一使用以下角色分工；每个硬件场景仍必须先获得单独授权：

```text
Terminal A: normal bringup
Terminal B: Flight Runtime
Terminal C: record_gate_evidence.py
Terminal D: gate-specific trigger / watchdog
Operator:   physical observation
End:        Ctrl+C recorder, then perform offline evidence review
```

Terminal C 的 recorder 只启动多个 `ros2 topic echo` 订阅并写入带时间戳的 session
目录，不 publish、不调用 service、不操作 authority、E-STOP、CAN、GPIO、PWM、motor 或
fan：

```bash
python3 scripts/hardware_verification/record_gate_evidence.py \
  --output-root ~/windarmor_evidence
```

它默认连续记录 authority、Flight command、motor feedback、安全状态、ownership 和 fan
PWM；JSON `--config` 或任意重复的 `--topic NAME=/topic:package/msg/Type` 都会**替换**
默认 topic 集，而不是追加。需要额外 topic 时，本地配置必须同时完整列出所需默认项和
额外项。看到 `READY` 后再进入 gate trigger；结束时按 `Ctrl+C`，manifest 会记录每个
child 的退出码、样本状态和停止时间。

`ros2 topic echo ... --once` 只等待订阅建立后的下一条消息，可以用于稳态抽查，但不
适合作为 ACTIVE、handoff、ownership 或 command transition 的唯一历史证据。这些瞬态
证据必须优先使用 continuous recorder；optional `--once` 文件缺失或为空不能覆盖已由
continuous log 捕获的有效最终状态。

operator physical observation 始终是独立 required evidence。场景结束后默认由人工离线
审查 trigger 记录、continuous ROS history、物理观察和退出后安全状态；只有人工判定容易
出错、条件复杂且重复执行价值明显时，才考虑新增 gate-specific analyzer。analyzer 不能
替代 physical observation，也不能单独宣布 hardware PASS；B2 已有 analyzer 不意味着
C1/C2/C3/C4 必须分别新增 analyzer。

`record_gate_evidence.py` 是长期通用 verification infrastructure。
`analyze_b2_evidence.py` 及其测试属于 v0.4.0 verification-cycle scoped tooling，在 Gate C、
Gate D 和本次 release 收口完成前暂时保留；v0.4.0 正式形成 tag/release 后，再由独立
cleanup task 判断是否从未来 master 删除。历史可追溯性由 Git tag/history 保留，不要求
旧 Gate 专用 analyzer 永久留在未来 master。

### 2.4 Global immediate-stop conditions

- logical motor、CAN ID、实际轴或方向不一致；
- 非批准轴运动、目标跳向零位、超出批准 offset 或接近机械干涉；
- fan 错侧、异常方向、非批准旋转或超过 Flight PWM 上限；
- fault bit、临界温度、CAN/serial 异常、owner/token/sequence 不一致；
- unexpected ACTIVE、旧 epoch/generation/target 重现或 legacy 自动恢复；
- E-STOP、watchdog、command lease 或 safe-stop 没有 fail-closed；
- 异常声音、振动、气味、温升、结构松动或日志丢失；
- 操作人或现场安全观察员要求停止。

立即发布系统急停（若 ROS 仍可用）：

```bash
ros2 topic pub --once /e_stop std_msgs/msg/Bool "{data: true}"
```

同时准备直接切断对应 actuator 动力。不得把 ROS 命令作为物理断电的替代。

### C3 — Graceful Runtime stop/restart and stale authority

【本阶段硬件状态】按单独批准的低幅 Gate B 场景供电。

【Trigger evidence】未来单独授权后，ACTIVE 后在 Runtime 终端按 `Ctrl+C`；保存旧进程
PID、完整 shutdown stdout/stderr 和退出码。若同一授权明确包含 restart，再保存新 PID 和
启动 transcript，证明它是新的 process/session；不得调用 prepare。

【Continuous ROS evidence】默认 recorder topics 足够，并须跨越 stop/restart 全过程持续
运行。required history 必须显示旧 executable gate 关闭、best-effort revoke 或 owner lease
后盾生效、motor halt、fan stop；新 Runtime 使用新的 authority epoch/session，状态为
DRY_RUN/NONE，且没有接受旧 epoch/generation/token/target。

【Operator physical evidence】记录 shutdown 时批准 actuator 是否及时 halt/stop、restart
期间是否有任何 motor/fan 自动动作、错侧动作，以及异常声音、振动、气味或温升。

【No automatic recovery evidence】restart 不得自动 prepare/ACTIVE，不得恢复旧 epoch、
generation、token、target 或 legacy owner；transport reconnect 也不得造成 actuator 动作。
只有另一次明确授权才可再次 prepare。

预期本地 executable gate 关闭、best-effort revoke、owner lease 后盾有效；restart 后必须
得到新的 authority epoch，状态为 DRY_RUN/NONE。

PASS：shutdown/restart 隔离成立。FAIL/立即停止：restart 后 ACTIVE、旧 token/target
恢复或 actuator movement。安全退出：`/e_stop=true`、确认停止、退出所有进程并断电。

### C4a — Owner loss

【本阶段硬件状态】按单独批准的低幅 Gate B 场景供电。C4a 与 C4b 必须单独授权，不连续
执行。

【Trigger evidence】未来单独授权后，使用正常 lifecycle transition；保存 CLI 完整
stdout/stderr 和退出码：

```bash
ros2 lifecycle set /imu_motor_controller_node deactivate
```

【Continuous ROS evidence】默认 recorder topics 足够。required history 必须显示 motor
safety `node_active=false`、motor owner/state 消失或释放、motor halt，Runtime 检测 mismatch
后 inhibit，并使 fan stop/revoke；CLI 成功不能替代这些结果。

【Operator physical evidence】记录 motor 是否及时 halt、fan 是否及时 stop、是否有未批准
motor movement、错侧 fan 或继续转动，以及异常声音、振动、气味或温升。

【No automatic recovery evidence】若未来同一授权明确包含 lifecycle 恢复，恢复后不得自动
ACTIVE，不得恢复旧 epoch/generation/token/target、legacy owner 或 actuator 动作；transport
reconnect 同样不得恢复旧 Flight。

PASS：owner loss trigger、两域 fail-closed 和无自动恢复分别有证据。FAIL/立即停止：任一
actuator 继续或恢复旧 authority。安全退出：保持 fail-closed，先断 fan/ESC、后断 motor
bus，再退出进程；恢复命令留到新的独立授权。

### C4b — E-STOP interaction

【本阶段硬件状态】按单独批准的低幅 Gate B 场景供电。C4b 不与 C4a 连续执行。

【Trigger and timing evidence】未来单独授权后，必须在 prepare 前启动预热 watchdog，并把
该 session 的 stdout/stderr 和真实进程退出码保存为正式 timing evidence。可使用普通
`tee`；`<SESSION_DIR>` 必须先替换为 recorder 打印的实际目录：

```bash
cd ~/workspace/WindArmor
source /opt/ros/jazzy/setup.bash
source install/setup.bash
set -o pipefail
python3 scripts/flight_estop_watchdog.py 2>&1 \
  | tee <SESSION_DIR>/c4b_estop_watchdog.log
watchdog_status=${PIPESTATUS[0]}
printf 'WATCHDOG_EXIT_STATUS=%s\n' "$watchdog_status" \
  | tee -a <SESSION_DIR>/c4b_estop_watchdog.log
test "$watchdog_status" -eq 0
```

只有看到 `WATCHDOG READY` 后，操作员才可在另一终端按该子场景单独授权执行 prepare。
watchdog 只在首次同时观察到 ACTIVE、FLIGHT_CONTROL 和 `actuation_allowed=true` 后启动
monotonic 2.0 秒计时，并由同一预热 publisher 发布一次 `/e_stop=true`；10 秒内无 ACTIVE
也会发布并报告 `NO ACTIVE WITHIN TIMEOUT`。它不调用 prepare/reset、不控制 ownership，
也不发送 motor/fan command。required watchdog log 必须包含 `WATCHDOG READY`、
`ACTIVE DETECTED`、`E-STOP PUBLISHED`、`ACTIVE_TO_PUBLISH_SEC`、
`ESTOP OBSERVED BY FLIGHT`、`PUBLISH_TO_INHIBIT_SEC` 和 exit status。缺少任一项均为
`NOT VERIFIED`/FAIL；exit code 0 本身不是 timing PASS。`NO ACTIVE WITHIN TIMEOUT` 是
fail-closed abort evidence，不是 ACTIVE-to-E-STOP PASS。

【Continuous ROS evidence】默认 recorder topics 足够，必须在 watchdog/prepare 前就绪并
持续记录完整历史：ACTIVE、E-STOP 后 authority INHIBITED、两 owner NONE、motor/fan
latch、安全输出及无旧 command 恢复。watchdog monotonic log 负责严格 timing，recorder
负责 ROS topic history，二者互不替代。不得退回人工盯高速 topic、临时 awk/grep pipeline
或 ACTIVE 后新启动 `ros2 topic pub --once` 作 timing measurement。

【Operator physical evidence】记录 E-STOP 后 motor/fan 是否及时 halt/stop、是否有未批准
motor movement、错侧 fan 或继续转动，以及异常声音、振动、气味或温升。

【No automatic recovery evidence】`/e_stop=false`、transport reconnect、Runtime restart 或
未来另行授权的 latch reset 都不得自动 ACTIVE，不得恢复旧 epoch/generation/token/target、
legacy owner 或 actuator 动作。

预期 lower-level E-STOP 优先，Flight authority 失效。`/e_stop=false`、transport reconnect
或 Runtime restart 都不得自动恢复 Flight。真实 destructive fault、堵转、过温、过流、
带电拔线不属于正常 RC，禁止执行。

PASS：watchdog timing、continuous ROS、物理停止和无自动恢复四类证据全部闭合。
FAIL/立即停止：任一 actuator 继续、timing 超界/缺失或恢复旧 authority。安全退出：保持
E-STOP latch，先断 fan/ESC、后断 motor bus，再退出进程；恢复命令留到新的独立授权。

## 6. Gate D — Legacy + Final RC Regression

【本阶段需要通电】Raspberry Pi/IMU/CAN、CyberGear motor bus、双 fan/ESC。

【本阶段必须保持断电】无，但首次上电仍按 motor 与 fan 分步完成，不能一次授权推定
全部已安全。

【上电前检查】Gate A–C 全部 PASS；Flight Runtime 已退出、两 owner 为 NONE；robot
固定、fan guard/净空、E-STOP/physical kill就绪；既有零点、方向和低幅动作获准。

【Terminal 1】

```bash
cd ~/workspace/WindArmor
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch windarmor_bringup windarmor.launch.py
```

预期：系统按 v0.3.2 legacy 默认启动，motor MANUAL，fan 无 MANUAL/AUTO 授权且 stop；
不得存在 Flight Runtime 或 `/flight_control/command` publisher。

【Terminal 2】

```bash
ros2 topic echo /motors/control_mode std_msgs/msg/String
ros2 topic echo /fans/control_state std_msgs/msg/String
ros2 topic echo /fans/status_pwm std_msgs/msg/Int32MultiArray
ros2 topic echo /motor/status std_msgs/msg/String
```

【Terminal 3】按每项单独批准顺序执行：

```bash
ros2 service call /imu/set_zero std_srvs/srv/Trigger "{}"
ros2 service call /motors/set_zero std_srvs/srv/Trigger "{}"
ros2 service call /fans/manual_enable std_srvs/srv/SetBool "{data: true}"
ros2 topic pub --once /fans/pwm std_msgs/msg/Int32MultiArray "{data: [800, 800]}"
ros2 service call /fans/auto_enable std_srvs/srv/SetBool "{data: true}"
ros2 topic pub --once /e_stop std_msgs/msg/Bool "{data: true}"
```

MANUAL motor、HOME、LEGACY_AUTO 通过既有 motor keyboard 分别作用户批准的小幅测试；
fan MANUAL 必须先建立本次授权后的 `[800,800]` baseline；fan AUTO 只在 motor AUTO、
状态新鲜且本次显式授权后验证。不要同时运行互相竞争的发布者。

预期物理行为：MANUAL/HOME/LEGACY_AUTO 方向与既有契约一致；fan左右映射、MANUAL/
AUTO、ramp 和 stop 正常；E-STOP 同时停止全部 actuator。绝对不应该发生：Flight
owner/command、旧 Flight target、E-STOP clear 后自动动作、ERROR/reconnect 自动恢复。

确认 E-STOP 原因已排除且全部设备静止后，恢复本身需要单独授权，并逐条观察状态：

```bash
ros2 topic pub --once /e_stop std_msgs/msg/Bool "{data: false}"
ros2 service call /enable_motor std_srvs/srv/SetBool "{data: true}"
ros2 service call /fans/enable std_srvs/srv/SetBool "{data: true}"
ros2 service call /fans/reset_e_stop std_srvs/srv/Trigger "{}"
ros2 service call /fans/manual_enable std_srvs/srv/SetBool "{data: true}"
ros2 topic pub --once /fans/pwm std_msgs/msg/Int32MultiArray "{data: [800, 800]}"
```

恢复后 motor 只到 MANUAL，fan 只到本次 neutral baseline；不得自动进入 AUTO 或恢复
旧 PWM。restart 测试必须先按安全退出顺序停止并重新执行 Terminal 1 命令，启动后
再次确认 MANUAL、fan disarmed/stop 和无 Flight owner。

【PASS】依次覆盖 motor MANUAL、LEGACY_AUTO、HOME，fan MANUAL、LEGACY_AUTO，
E-STOP、shutdown、restart、explicit legacy reclaim 和 final normal regression；每项
都有实测证据且无回归。任一项 FAIL 或 NOT VERIFIED 都不得进入 RC/release。

【FAIL / 立即停止】任何模式/方向/通道错误、异常动作、安全机制退化、旧 Flight
authority 恢复或 shutdown 后输出残留。

【安全退出】

1. 发布 `/e_stop=true` 并确认 motor `EMERGENCY_STOP`、fan `[800,800]`；
2. 先断 fan/ESC 动力，再断 motor bus；
3. Terminal 1 按 `q` 或 `Ctrl+C`，确认全部 node 退出；
4. 最后断逻辑电源并保存日志、配置 snapshot 和 PASS/FAIL 记录。

Gate D 全部 PASS 后才允许进入 v0.4.0 RC/release 收口；这仍不自动授权 commit、push、
tag 或 GitHub Release。
